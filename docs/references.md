# Références (recherche du 1er novembre 2026)

## install-vps

**Recommandation.** Je recommande deux portes d'entrée qui mènent au même premier écran. Les deux reposent sur un seul docker-compose.yml public qui ne demande aucune variable, et sur des images préconstruites sur GHCR, multi-architecture et signées.

PORTE 1, HOSTINGER (le vrai un clic)
Un badge « Deploy on Hostinger » sur le site et dans le README, qui pointe vers :
https://www.hostinger.com/docker-hosting?compose_url=https://raw.githubusercontent.com/<org>/noah/main/deploy/docker-compose.yml
Le dépôt réel est à substituer. Ajouter &REFERRALCODE=… si on veut l'affiliation.

PORTE 2, N'IMPORTE QUEL VPS
curl -fsSL https://<site-noah>/install.sh | sh
Le script fait ce que fait celui de Coolify : il installe Docker si besoin, crée /opt/noah, télécharge le même compose et lance docker compose pull puis up -d. Plus aucun build sur le VPS : install.sh --domaine reste en option.

Au premier démarrage, un conteneur d'initialisation, ou le lanceur lui-même :
- détecte l'IP publique ;
- écrit le Caddyfile avec le nom <ip-en-tirets>.sslip.io (nip.io en secours si la limite de Let's Encrypt est atteinte, certificat d'IP shortlived en dernier recours) ;
- génère les secrets (équivalent de WEBUI_SECRET_KEY, stockés dans un volume et jamais régénérés) ;
- génère un code d'installation à usage unique, affiché dans les logs et dans la sortie du script.

On évite ainsi la faille de Coolify et de Dokploy, où le premier visiteur devient root.

SÉQUENCE VÉCUE, PORTE HOSTINGER
1. Sur le site de Noah, l'utilisateur clique « Déployer sur Hostinger ».
2. Il arrive sur la page Docker Hosting de Hostinger avec Noah préchargé. Il choisit un plan (KVM 2, 8 Go, conseillé : Camoufox par agent ; Hostinger annonce environ 1 Go pour le seul conteneur Hermes, plus avec le navigateur) et paie.
3. Hostinger prépare le VPS avec Docker. Docker Manager s'ouvre avec le compose de Noah chargé et l'aperçu YAML.
4. Il clique Deploy. Le tirage des images GHCR et le démarrage prennent quelques minutes.
5. Dans le projet, il ouvre les logs (ou le bouton Open). On y lit : « Noah est prêt : https://203-0-113-7.sslip.io/bienvenue, code 4F7K-92QD ».
6. Il ouvre l'URL : HTTPS valide, cadenas, aucun avertissement.

Assistant façon Home Assistant, avec le code demandé en premier :
- a. Saisir le code d'installation.
- b. Choisir « Nouvelle installation » ou « Restaurer une sauvegarde » (migration depuis l'app Electron).
- c. Créer le compte propriétaire, avec un avertissement : mot de passe non récupérable.
- d. Choisir le modèle : clé d'un fournisseur au choix, ou modèle local (Ollama) ; aucune télémétrie, désactivée par défaut.
- e. Créer le premier agent.
- f. Régler la fenêtre de mise à jour (par défaut la nuit, heure locale, à la manière de l'Auto Update Frequency en cron de Coolify), avec mise à jour seulement si aucun agent n'a de tâche en cours.
- g. Écran « Relier vos appareils » : QR code pour l'app mobile et code d'appairage pour l'app de bureau, qui pointent vers le nom sslip.io. Le Wi-Fi n'est plus nécessaire.

SÉQUENCE VÉCUE, PORTE SCRIPT
Le VPS est acheté n'importe où. L'utilisateur se connecte en SSH (ou ouvre le terminal web de l'hébergeur), colle la commande, et le script se termine sur la même ligne « https://…sslip.io/bienvenue, code … ». La suite est identique à partir de l'étape 6.

À FAIRE AUSSI
- Garder --domaine pour ceux qui ont un domaine : Caddy bascule simplement sur ce nom.
- Plus tard, une PR de modèle Coolify, réservée aux projets d'au moins 1 000 étoiles.
- Voir si l'API Hostinger (POST /api/vps/v1/virtual-machines/{id}/docker) permettrait à l'app de bureau de déployer elle-même sur le VPS. Non vérifié sur la doc officielle.

- **Hostinger, bouton « Deploy on Hostinger »** (https://www.hostinger.com/support/deploy-on-hostinger-button) : C'est la vraie porte d'entrée en un clic pour un projet open source. Le lien envoie vers la page Docker Hosting de Hostinger avec le fichier compose du projet déjà chargé. L'utilisateur paie, le VPS se prépare avec Docker, puis Docker Manager s'ouvre avec le compose prêt à déployer. Modèle d'URL cité tel quel : https://www.hostinger.com/docker-hosting?compose_url=docker-compose-url&REFERRALCODE=code. Le badge est https://assets.hostinger.com/vps/deploy.svg. L'exemple de la doc pointe vers un docker-compose.yml brut sur GitHub. La doc ne dit pas si des variables d'environnement sont demandées à l'utilisateur, ni si un dépôt privé fonctionne : non trouvé, à tester.
- **Hostinger Docker Manager (Compose from URL / One click deploy)** (https://www.hostinger.com/support/12040815-how-to-deploy-your-first-container-with-hostinger-docker-manager/) : Sur un VPS existant : VPS > Manage > Docker Manager > Compose > « Compose from URL », on colle l'URL du compose (GitHub, GitLab ou lien direct), on voit l'aperçu YAML, puis Deploy. Hostinger valide le fichier, tire les images et démarre les services, en 30 s à 2 min selon la doc. La doc ne prévoit pas de champ de variables d'environnement pour le mode URL, donc les valeurs doivent être dans le compose ou générées au démarrage. L'application est servie sur http://IP-du-VPS:port selon le mappage de ports. Prérequis : un VPS installé avec le modèle Docker.
- **Hostinger, liste des modèles et du catalogue Docker** (https://www.hostinger.com/support/1583571-what-are-the-available-operating-systems-for-vps-at-hostinger/) : Il existe des modèles d'OS prêts (Coolify, Dokploy, Dokku, Portainer, Cosmos Cloud, n8n, NemoClaw…) et un catalogue Docker (Ubuntu 24.04 + Docker) qui contient déjà Hermes Agent, OpenClaw, Ollama et Home Assistant. CasaOS, Umbrel et Open WebUI ne figurent pas dans cette liste. Hermes Agent est déjà dans le catalogue de Hostinger : c'est un concurrent direct dans le même parcours, et un modèle à copier. Je n'ai trouvé aucune procédure publique pour faire entrer un projet tiers dans le catalogue.
- **Hostinger, Hermes Agent depuis le catalogue** (https://www.hostinger.com/support/how-to-get-started-with-hermes-agent-on-hostinger-vps/) : Docker Manager > Catalog > Hermes Agent > Select. On saisit un identifiant et un mot de passe admin, une clé API en option (préremplie si l'utilisateur a acheté les crédits Hostinger AI Router ou Oxylabs), puis Deploy. Hermes et les services d'appui, dont Traefik, sont créés. On accède à l'agent par le bouton « Open », qui ouvre la CLI Hermes dans le conteneur. Le premier lancement passe par un assistant CLI : mode Full setup, fournisseur de modèle, canaux, outils. La page produit (https://hostinger.com/vps/docker/hermes-agent) annonce aussi un tableau de bord web et des « One-click updates », avec KVM 1 (4 Go) à 6,49 $/mois et KVM 2 (8 Go) à 8,79 $/mois sur 24 mois payés d'avance.
- **Hostinger, OpenClaw sur VPS** (https://www.hostinger.com/support/how-to-install-openclaw-on-hostinger-vps-template-installation/) : Parcours complet de l'achat à la première page : choix du plan (KVM2 conseillé), OpenClaw présélectionné au paiement, crédits IA en option, puis écran de configuration (jeton de passerelle généré automatiquement, clés API en option, numéro WhatsApp). Ensuite Deploy, et l'application apparaît avec ses ports. L'accès se fait par défaut en http://IP:port, et la connexion demande OPENCLAW_GATEWAY_TOKEN. Sans HTTPS, l'erreur « control ui requires device identity (use HTTPS or localhost secure context) » apparaît. Leçon pour Noah : une PWA, le presse-papiers et les service workers exigent un contexte sécurisé, donc le HTTPS doit être en place dès la première page.
- **Hostinger, SSL d'OpenClaw par Traefik et sous-domaine automatique** (https://www.hostinger.com/support/how-to-add-ssl-to-openclaw-on-hostinger/) : Docker Manager > « Deploy Traefik », saisie de ACME_EMAIL, puis Open. Le tableau de bord passe en HTTPS sur un sous-domaine attribué automatiquement, sans nom de domaine acheté. L'exemple donné est https://openclaw-xxxx.srv123456.hstgr.cloud. Le compose d'OpenClaw porte des labels Traefik préconfigurés, mais ils ne sont pas publiés et la doc ne dit pas si une application tierce avec des labels en profite. Point de vigilance : ce Traefik écoute sur 80 et 443, comme le Caddy de Noah.
- **Hostinger API (Docker Manager)** (https://pypi.org/project/hostinger-api/) : Le SDK officiel expose la création d'un projet Docker à partir d'un contenu compose ou d'une URL. Une app de bureau pourrait donc déployer Noah sur le VPS de l'utilisateur avec sa clé API Hostinger. Selon le SDK et des miroirs tiers : POST /api/vps/v1/virtual-machines/{virtualMachineId}/docker, avec les paramètres project_name, content et environment en option. Je n'ai pas lu la page officielle developers.hostinger.com, donc la forme exacte de la requête n'est pas vérifiée.
- **Coolify, script curl | bash** (https://coolify.io/docs/get-started/installation) : Une seule commande : curl -fsSL https://cdn.coollabs.io/coolify/install.sh | bash. Le script installe curl, wget, git, jq et openssl, installe Docker Engine, règle les journaux de Docker, crée /data/coolify, configure les clés SSH et démarre Coolify. La fin affiche « Congratulations! » avec http://<ip>:8000. Faille documentée : la première personne qui atteint la page d'inscription devient admin avec un accès root. Parade : ROOT_USERNAME, ROOT_USER_EMAIL et ROOT_USER_PASSWORD passés en env créent l'admin d'avance. Mises à jour auto (https://coolify.io/docs/core/instance-management/update) : interrupteur Auto Update, fréquence en cron (par défaut 0 0 * * *, à minuit heure de l'instance), vérification séparée toutes les heures, réglage surchargé par AUTOUPDATE dans /data/coolify/source/.env.
- **Coolify, modèles de services en un clic** (https://coolify.io/docs/contribute/service) : On ajoute un <service>.yaml dans /templates/compose, avec le logo, par une PR. Les variables magiques SERVICE_FQDN_<SERVICE>_<PORT> donnent automatiquement un nom d'hôte. La doc de la branche next exige au moins 1 000 étoiles GitHub pour entrer au catalogue en un clic, ainsi qu'une PR de documentation. Le port principal doit figurer dans l'en-tête. C'est un canal secondaire pour les gens qui ont déjà Coolify (modèle d'OS proposé par Hostinger).
- **Dokploy** (https://docs.dokploy.com/docs/core/installation) : curl -sSL https://dokploy.com/install.sh | sh installe Docker si besoin et la dernière version stable, puis http://IP:3000 redirige vers la page de création du compte admin. Le script échoue si les ports 80, 443 ou 3000 sont pris (Traefik sur 80/443). Après l'admin, la doc conseille de configurer un domaine HTTPS puis de fermer le port 3000. On y retrouve la même fenêtre du « premier arrivé » que chez Coolify.
- **CasaOS** (https://github.com/IceWhaleTech/CasaOS) : curl -fsSL https://get.casaos.io | sudo bash, sur Debian 12 (conseillé), Ubuntu Server 20.04 ou Raspberry Pi OS. La mise à jour passe par l'interface (Settings > Update) ou par curl -fsSL https://get.casaos.io/update | sudo bash. Le README ne décrit ni l'URL ou le port obtenus après l'installation, ni la création du premier compte : non trouvé. 821 issues sont ouvertes et je n'ai pas pu lire la date de la dernière release. Ce n'est pas un modèle d'OS chez Hostinger.
- **Umbrel** (https://community.umbrel.com/t/install-umbrelos-on-a-vps/16715) : Ancienne méthode : curl -L https://umbrel.sh | bash sur Ubuntu/Debian, qui installe Docker et Umbrel. Les messages du forum (2024) disent qu'umbrelOS est passé à des images à graver sur clé USB, et que la plupart des VPS ne démarrent pas une image personnalisée. Il reste une image communautaire dockurr/umbrel. Je n'ai pas pu confirmer l'état en 2026. Ce n'est pas un bon modèle pour un VPS.
- **Open WebUI (image GHCR, premier compte admin)** (https://docs.openwebui.com/getting-started/quick-start/) : Pas de build : docker run ... ghcr.io/open-webui/open-webui:main. Le premier compte créé devient administrateur, puis l'inscription se ferme. La doc demande de fixer WEBUI_SECRET_KEY (openssl rand -hex 32) une fois pour toutes, sinon chaque recréation du conteneur déconnecte tout le monde. La mise à jour se fait par Watchtower en une passe (nickfedor/watchtower --run-once open-webui). Il n'y a pas de script d'installation pour Open WebUI lui-même : non trouvé.
- **Home Assistant, assistant de premier lancement** (https://www.home-assistant.io/getting-started/onboarding/) : Cinq écrans dans l'ordre : Bienvenue (nouvelle installation ou restauration d'une sauvegarde), compte propriétaire, lieu (fuseau horaire, unités, devise), statistiques (désactivées par défaut), puis appareils découverts et Finish. Deux bonnes idées à reprendre : proposer « Restaurer une sauvegarde » dès le premier écran (utile pour migrer de l'app Electron vers le VPS), et un partage de données désactivé par défaut, cohérent avec le public de Noah.
- **nip.io / sslip.io** (https://nip.io/) : Un nom comme 64-176-22-9.nip.io (ou sslip.io) se résout vers l'IP qu'il contient. On peut obtenir un certificat Let's Encrypt pour ce nom par HTTP-01 avec un serveur web sur la machine, Caddy cité en exemple. Les deux domaines sont interchangeables et tenus par les mêmes personnes depuis 2025. Pas de certificat wildcard. Let's Encrypt a relevé la limite du service à 250 000 certificats et refusé 500 000. En cas de limite atteinte, le site conseille de basculer sur l'autre domaine ou sur un certificat d'IP. Prévoir les deux en secours.
- **Let's Encrypt, certificats d'adresse IP** (https://letsencrypt.org/2026/01/15/6day-and-ip-general-availability) : Depuis le 15 janvier 2026, les certificats pour une IPv4 ou une IPv6 sont disponibles pour tous. Ils durent 160 heures et imposent le profil ACME shortlived. Il faut un client ACME compatible avec les profils. Pour Caddy (https://github.com/caddyserver/caddy/issues/7399, fermée le 25/04/2026), le bug venait d'une liste blanche d'autorités périmée. L'issue confirme le correctif sur master mais ne nomme pas de version publiée. Syntaxe : tls { issuer acme https://acme-v02.api.letsencrypt.org/directory { profile shortlived } }. C'est un plan B : le nom sslip.io reste plus simple et plus stable.
- **Caddy, HTTPS automatique et on-demand TLS** (https://caddyserver.com/docs/automatic-https) : HTTPS automatique dès que Caddy connaît le nom, avec les ports 80 (HTTP-01) et 443 (TLS-ALPN-01) ouverts. Le on-demand TLS obtient le certificat pendant la poignée de main TLS, filtré par un endpoint « ask ». Sans configuration, Caddy sert une IP nue avec un certificat auto-signé que personne ne reconnaît. Le on-demand TLS est inutile pour un seul nom connu d'avance : il suffit d'écrire le nom sslip.io dans le Caddyfile au premier démarrage. Si on l'utilise un jour (domaines perso ajoutés plus tard), l'endpoint ask est obligatoire pour éviter qu'un attaquant remplisse le disque de certificats.
- **GitHub Actions vers GHCR** (https://docs.github.com/en/actions/tutorials/publish-packages/publish-docker-images) : Construire et publier ghcr.io/<owner>/<image> à chaque release avec GITHUB_TOKEN, docker/metadata-action, docker/build-push-action et actions/attest. Le VPS ne construit plus rien, il tire les images. Permissions : packages: write, contents: read, attestations: write, id-token: write. La page ne traite pas de la visibilité : il faut rendre le paquet public à la main pour qu'un VPS le tire sans s'authentifier (à vérifier dans les réglages du paquet).

**Pièges.**
- Conflit de ports 80 et 443 : si l'utilisateur a déployé le Traefik de Hostinger (celui de l'Auto-SSL d'OpenClaw et de Hermes), le Caddy de Noah ne démarre pas. Il faut le détecter et l'expliquer, ou proposer un mode « derrière Traefik » avec des labels et un sous-domaine *.srvNNNN.hstgr.cloud. Ce dernier mode n'est pas documenté pour les applications tierces.
- Docker Manager ne connaît que les conteneurs du compose. Les conteneurs Hermes et Camoufox lancés par le lanceur via /var/run/docker.sock seront hors projet : l'Update et le Delete de Hostinger ne les toucheront pas, et monter le socket donne un accès root à l'hôte. Il faut le documenter.
- La fenêtre du « premier arrivé devient admin » (Coolify le documente explicitement, et c'est le même modèle chez Dokploy et Open WebUI) est réelle sur un VPS public. Le code d'installation est obligatoire.
- Limites de Let's Encrypt sur sslip.io : 250 000 certificats partagés par tous les utilisateurs du service. Il faut garder nip.io et le certificat d'IP shortlived en secours, et ne jamais redemander un certificat à chaque redémarrage (garder le volume /data de Caddy).
- Certificats d'IP : 160 h seulement, et la prise en charge dans Caddy n'est confirmée que sur master (issue 7399) sans version publiée nommée. Il ne faut pas en faire la voie principale.
- Un HTTP nu casse la PWA : OpenClaw affiche « requires … secure context » sans HTTPS. Il ne faut jamais montrer l'URL http://IP:port comme première page.
- Hostinger ne documente pas si compose_url accepte un dépôt privé ni s'il demande des variables à l'utilisateur. Il faut tester avant de communiquer.
- Hermes Agent est déjà dans le catalogue Docker de Hostinger, avec admin et crédits IA de Hostinger. Il faut dire clairement ce que Noah ajoute (multi-agent, navigateur par agent, apps, aucune donnée chez les grands fournisseurs) et ne pas reproduire le parcours CLI de Hermes.
- Umbrel ne convient pas aux VPS (images USB que la plupart des hébergeurs ne démarrent pas), et CasaOS ne documente ni son premier écran ni sa dernière release : à ne pas prendre comme base.
- Les paquets GHCR sont privés par défaut quand on les crée dans une organisation ou un compte. Il faut les rendre publics, sinon le pull échoue sur le VPS (la doc GitHub lue ne couvre pas ce point).

## appairage

**Recommandation.** Recommandation pour Noah Agent : un QR code qui contient l'URL et un jeton à usage unique, avec deux voies de secours.

1. Voie principale, le QR depuis l'interface web déjà connectée (modèle OpenClaw et RFC 8628).
- Contenu : noahagent://pair?u=https://agent.domaine.tld#t=<jeton>. Le jeton est mis après le # (le fragment), parce que les navigateurs n'envoient jamais le fragment au serveur : il n'apparaît donc pas dans les journaux de Caddy.
- Le jeton est aléatoire (au moins 128 bits), à usage unique et valable 10 min, comme OpenClaw et Jellyfin.
- Le serveur n'en garde que le hachage SHA-256.
- On peut ajouter l'empreinte du certificat. Elle n'est pas indispensable avec Let's Encrypt, et elle casse au renouvellement si on épingle le certificat feuille.
- Le même lien sert de lien profond sur Android (intent filter), et le QR fonctionne sur 4G : le VPS est public, il n'y a besoin ni de Wi-Fi ni de mDNS.

2. L'échange du jeton. L'app génère sa propre paire de clés (Android Keystore, ou trousseau de l'OS sur le bureau) et envoie le jeton, sa clé publique, son nom et sa plateforme. Le serveur renvoie un jeton d'appareil long et révocable, ou mieux un refresh token (90 jours glissants) avec un jeton d'accès court (30 min), comme Home Assistant. On ne renvoie jamais le mot de passe du compte.

3. Secours n°1, l'app de bureau. Elle fait comme Nextcloud Login Flow v2 : POST /api/pair/start, ouverture du navigateur sur le VPS, connexion avec la 2FA, clic sur « Autoriser cet appareil », puis sondage jusqu'au jeton (validité 20 min, réponse donnée une seule fois). L'utilisateur n'a rien à copier : il tape l'URL et confirme dans le navigateur.

4. Secours n°2, un code tapé à la main. C'est pour une TV ou quand la caméra est absente. Le nouvel appareil affiche un code, comme Quick Connect de Jellyfin ou le device grant de la RFC 8628, et un appareil déjà connecté le valide.
- Le code fait 8 caractères en base 20 (« WDJB-MJHT ») plutôt que 6 chiffres, et vit 10 min.
- Il est limité à 5 essais, et l'écran d'accord affiche le type et le nom de l'appareil demandeur.

Pourquoi pas les 6 chiffres seuls ? Cela fait environ 20 bits. Jellyfin n'a aucune limite de tentatives dans son code, et 6 chiffres exposés sur Internet sans limite, c'est trop faible. Le code à saisir n'est donc qu'un secours.

Pourquoi pas un simple champ URL avec un mot de passe, comme Bitwarden ? Il faut le garder pour les experts, mais c'est la voie la plus lente et elle fait circuler le mot de passe principal.

Ce que Noah doit éviter :
- Plex, qui dépend d'un service central ;
- Tailscale, qui dépend d'un compte tiers (Headscale n'a pas été étudié ici) ;
- un lien profond qui transporte un mot de passe durable, comme le nc:// de Nextcloud Flow v1.

Stockage, liste et révocation des jetons d'appareil :
- Côté serveur, une table devices : id, user_id, nom, plateforme, version de l'app, hachage du jeton (jamais le jeton en clair, alors qu'OpenClaw garde des secrets dans sa base SQLite), clé publique, created_at, last_seen_at, last_ip, scopes.
- Une page « Appareils » liste les appareils avec leur dernière activité, et un bouton les révoque : la ligne est supprimée, les WebSocket et les jetons d'accès dérivés sont coupés immédiatement, comme le POST /auth/revoke de Home Assistant.
- Révoquer un lien ou un code d'appairage ne révoque pas les appareils déjà entrés, comme chez OpenClaw et Tailscale. Il faut le dire dans l'interface.
- Il faut aussi proposer « Déconnecter tous les appareils » et la rotation du jeton (openclaw devices rotate).
- Dans l'app, un appel DELETE /api/devices/self au moment de « Oublier ce serveur ». Si l'appel échoue, on efface quand même en local, comme le recommande Nextcloud.
- Sur Android, le jeton est stocké avec le Keystore : EncryptedSharedPreferences est déprécié depuis 2025.
- Sur Electron, le trousseau de l'OS (safeStorage). Ce point n'a pas été vérifié dans cette recherche.

Non trouvé ou non confirmé : le mécanisme de stockage des jetons dans l'app Android d'OpenClaw, la durée de validité officielle du code Plex, la prise en charge de « Log in with device » de Bitwarden en auto-hébergé ou par Vaultwarden, et l'effacement à distance de Nextcloud.

- **OpenClaw (passerelle + nœuds / apps compagnons)** (https://docs.openclaw.ai/gateway/pairing) : Lien ou QR d'appairage (oc-pair://<setup-code>) qui contient l'adresse de la passerelle, un jeton d'amorçage à usage unique et l'empreinte TLS. L'appareil a sa propre paire de clés (device ID + clé publique). L'admin approuve sur la passerelle, puis l'appareil reçoit un jeton d'appareil. Le QR n'est pas gardé dans l'historique du chat ni dans le cache du navigateur. Jeton d'amorçage valable 10 min. Une demande d'appairage en attente expire au bout de 5 min. Commandes : `openclaw devices list` / `approve <id>` / `reject <id>`, `openclaw nodes pending|approve|status`, `openclaw devices rotate` (RPC device.token.rotate), `openclaw nodes remove --node <id>` (RPC node.pair.remove : retire le rôle, coupe les sessions). Les jetons d'appareil sont dans ~/.openclaw/state/openclaw.sqlite (« secrets », à protéger). Révoquer le lien d'appairage ne révoque pas l'appareil. Approbation automatique possible par plage CIDR (gateway.nodes.pairing.autoApproveCidrs), désactivée par défaut. La doc ne donne pas de commande qui liste les jetons eux-mêmes.
- **OpenClaw app Android** (https://docs.openclaw.ai/platforms/android) : Découverte mDNS/NSD (_openclaw-gw._tcp) sur le réseau local, ou DNS-SD étendu via Tailscale, ou saisie manuelle. Bouton « Scan QR or setup code ». Le code se génère dans l'UI (Devices > Pair device) ou avec `openclaw qr` (options --remote, --limited). Le code donne un accès opérateur complet en wss:// ; en ws:// non local, l'accès est limité. Le ws:// en clair n'est accepté que sur LAN privé, .local et loopback. Tout est stocké par passerelle (identifiants, jeton d'appareil, empreinte TLS, chats), et « Forget » efface tout. La doc ne dit pas quel stockage Android est utilisé.
- **Nextcloud Login Flow v2** (https://docs.nextcloud.com/server/latest/developer_manual/client_apis/LoginFlow/index.html) : Le client fait un POST anonyme sur /index.php/login/v2 et reçoit une URL de connexion et un jeton de sondage. L'utilisateur se connecte dans son navigateur (2FA compris) et clique « Grant access ». Pendant ce temps, le client interroge /login/v2/poll et finit par recevoir {server, loginName, appPassword}. C'est le modèle idéal pour une app de bureau. Jeton de sondage valable 20 min. Le serveur répond 404 tant que l'accès n'est pas accordé, puis 200 une seule fois. Chaque client reçoit son propre app password, nommé d'après son User-Agent. Révocation côté client : DELETE /ocs/v2.php/core/apppassword. L'ancien Flow v1 passe par une webview et le lien profond nc://login/server:..&user:..&password:.. (déconseillé : secret dans un schéma d'URL).
- **Nextcloud gestion des appareils** (https://docs.nextcloud.com/server/latest/user_manual/en/session_management.html) : Paramètres perso > Sécurité : liste des navigateurs et appareils connectés récemment, avec un menu pour déconnecter chacun. On peut créer un mot de passe par appareil, montré une seule fois. Le mot de passe d'appareil n'est pas conservé après sa création. Avec la 2FA, seuls les mots de passe d'appareil marchent pour les clients. Changer le mot de passe dans un annuaire externe invalide les mots de passe d'appareil jusqu'à la prochaine connexion. Effacement à distance : pas confirmé sur cette page.
- **Jellyfin Quick Connect** (https://jellyfin.org/docs/general/server/quick-connect/) : Le nouvel appareil affiche un code temporaire. Un appareil déjà connecté le saisit dans Paramètres > Quick Connect et confirme. Le nouvel appareil se connecte alors tout seul, sans mot de passe. L'admin peut couper la fonction pour tout le serveur. Code source (QuickConnectManager.cs, https://raw.githubusercontent.com/jellyfin/jellyfin/master/Emby.Server.Implementations/QuickConnect/QuickConnectManager.cs) : Timeout = 10 min, CodeLength = 6, code tiré de RandomNumberGenerator entre 100000 et 999999. Secret de sondage de 32 octets en hexadécimal. Aucune limite de tentatives dans ce fichier, et aucune vérification de collision entre codes.
- **Home Assistant Companion (découverte + URL)** (https://developers.home-assistant.io/docs/api/instance_discovery) : Le serveur s'annonce en mDNS sous _home-assistant._tcp.local. avec internal_url et external_url dans le TXT. L'app trouve le serveur toute seule sur le Wi-Fi, sinon l'utilisateur tape l'adresse (https://companion.home-assistant.io/docs/getting_started/). L'app choisit l'URL interne ou externe selon le SSID (ou le BSSID) du Wi-Fi, ce qui demande la permission de localisation « tout le temps » (https://companion.home-assistant.io/docs/troubleshooting/networking/). Pour Noah sur VPS, c'est surtout un contre-exemple : une seule URL HTTPS publique évite toute cette complexité.
- **Home Assistant Auth API (jetons)** (https://contributors.home-assistant.io/core/internals/auth-api/) : OAuth2 avec code d'autorisation (/auth/authorize puis /auth/token, PKCE S256 recommandé). Le client_id est l'URL de l'app, ce qui évite d'enregistrer les clients à l'avance. Le jeton d'accès est court et le refresh token est révocable. Jeton d'accès : expires_in 1800 s. Le refresh token expire après 90 jours sans usage. Révocation : POST /auth/revoke token=..., qui révoque aussi les jetons d'accès dérivés et répond toujours 200. Jetons longue durée : 10 ans, créés depuis le profil ou par WebSocket, montrés une seule fois. Métadonnées publiées sur /.well-known/oauth-authorization-server (RFC 8414).
- **Bitwarden / Vaultwarden (URL de serveur auto-hébergé)** (https://bitwarden.com/help/change-client-environment/) : Sur l'écran de connexion, un menu « Logging in on » propose bitwarden.com, bitwarden.eu ou Self-hosted. On y saisit l'URL https:// du serveur, avec option de certificat client sur mobile. Chaque compte peut viser un serveur différent sur le bureau. Champs avancés « Custom Environment » (api, identity, notifications...). CLI : `bw config server https://...`. Le choix de serveur est un simple champ, sans découverte ni QR. « Log in with device » (https://bitwarden.com/help/log-in-with-device/) : la demande est approuvée depuis un appareil déjà connecté après comparaison d'une phrase d'empreinte propre à la demande, et expire en 15 min. Cette page ne dit pas si cela marche en auto-hébergé ni avec Vaultwarden.
- **Plex (code de liaison)** (https://www.plex.tv/link/) : L'app affiche un code court de 4 caractères. L'utilisateur, connecté à son compte, le saisit sur plex.tv/link, et l'app récupère le jeton par sondage. API (forum officiel https://forums.plex.tv/t/authenticating-with-plex/609370) : POST plex.tv/api/v2/pins (strong=true pour un code long via app.plex.tv/auth), puis GET /api/v2/pins/{id} jusqu'à ce que authToken soit rempli. Durée de 30 min selon un gist communautaire seulement (non officiel). Une variante JWT signée par l'appareil (2025) n'est citée que par un agrégateur (apis.io) : non vérifiée dans la doc officielle. Cela dépend d'un service central plex.tv, à l'opposé de l'objectif de Noah.
- **Tailscale (clés d'auth, expiration des nœuds)** (https://tailscale.com/kb/1085/auth-keys) : Clés à usage unique (révoquées dès qu'elles servent), réutilisables, éphémères ou pré-approuvées, avec des tags. Pratique pour relier un appareil à un réseau privé sans ouvrir de port. Expiration de la clé entre 1 et 90 jours (90 par défaut). Révoquer une clé ne déconnecte pas les nœuds déjà entrés : il faut les supprimer dans Machines. La clé d'un nœud expire après 180 jours par défaut. Bonne leçon de conception : la clé d'entrée et l'identité de l'appareil sont deux choses séparées. Mais Tailscale demande un compte chez un tiers (sauf avec Headscale, non étudié ici).
- **RFC 8628 (Device Authorization Grant)** (https://datatracker.ietf.org/doc/html/rfc8628) : Le standard derrière les codes à saisir : un code utilisateur court, un device_code secret et long, du sondage, et verification_uri_complete affichable en QR. Recommandations : 8 caractères en base 20 (BCDFGHJKLMNPQRSTVWXZ, environ 34,5 bits) ou 9 chiffres. Limiter les tentatives (environ 5 essais par code). Normaliser la saisie (tirets, majuscules). Sondage toutes les 5 s par défaut, avec slow_down. Risque principal : le phishing à distance, où un attaquant lance l'appairage et fait saisir son code à la victime. Parades : afficher le nom et le type d'appareil, faire confirmer que le code affiché correspond, garder une durée de vie courte.
- **Android Keystore / EncryptedSharedPreferences** (https://developer.android.com/jetpack/androidx/releases/security) : Pour garder le jeton d'appareil sur Android, Google recommande maintenant les API de la plateforme et le Keystore Android directement. androidx.security:security-crypto (EncryptedSharedPreferences) est déprécié depuis 1.1.0-alpha07 (9 avril 2025), et la stable 1.1.0 est sortie le 30 juillet 2025. À ne pas utiliser dans du code neuf : chiffrer avec une clé AES du Keystore (non exportable), ou passer par un plugin de stockage sécurisé de la plateforme choisie (non étudié ici).

**Pièges.**
- Code à 6 chiffres exposé sur Internet sans limite de tentatives : environ 20 bits, donc devinable. Jellyfin n'en limite aucune dans QuickConnectManager. Il faut une limite par code et par IP, ou un code plus long (8 caractères en base 20 selon la RFC 8628).
- Phishing à distance (RFC 8628) : un attaquant lance un appairage et fait valider son code par la victime. Il faut afficher l'appareil demandeur et faire confirmer que le code correspond.
- Mettre le jeton dans la query string d'une URL https (?t=...) : il finit dans les journaux de Caddy, l'historique du navigateur et l'en-tête Referer. Utiliser le fragment # ou un POST.
- Mettre un secret durable dans un lien profond (nc://...password:...) : une autre app peut déclarer le même schéma et l'intercepter. N'y mettre qu'un jeton court à usage unique, et préférer les App Links Android vérifiés quand c'est possible.
- Confondre le jeton d'appairage et le jeton d'appareil : chez OpenClaw et Tailscale, révoquer la clé d'entrée ne déconnecte pas les appareils déjà entrés. Il faut deux actions distinctes dans l'interface.
- Stocker les jetons d'appareil en clair côté serveur : OpenClaw les garde dans SQLite et prévient que la base est sensible. Il vaut mieux ne garder que le hachage.
- Épingler le certificat feuille alors que Caddy renouvelle Let's Encrypt automatiquement : l'épinglage casse tous les 60 à 90 jours. Avec une CA publique, ne pas épingler, ou épingler une clé stable.
- Utiliser EncryptedSharedPreferences (déprécié depuis avril 2025) dans du code Android neuf.
- Copier la découverte mDNS ou SSID de Home Assistant : elle est inutile pour un VPS public, et elle exige la permission de localisation en arrière-plan sur Android.
- Dépendre d'un service central d'appairage (plex.tv, compte Tailscale) : cela contredit la promesse « vos données ne passent pas chez un tiers ».
- Jetons sans expiration (les jetons longue durée de Home Assistant valent 10 ans) : préférer un refresh token glissant (90 jours sans usage) avec un jeton d'accès court.
- Les sources non officielles (gist Plex sur les 30 min, apis.io sur le JWT Plex, guides tiers OpenClaw) n'ont pas été confirmées dans la documentation officielle.

## mobile

**Recommandation.** PILE RECOMMANDÉE : Capacitor 8, Web Push (VAPID) côté serveur, UnifiedPush sur Android, APNs sur iOS (plus tard).

1) Emballage : Capacitor 8 autour du build Vite existant. C'est la seule option qui reprend le frontend React/PWA sans réécriture. Expo/RN oblige à migrer la navigation et pousse vers Expo Push Service, donc un tiers. Tauri mobile n'a pas de push officiel et le push iOS y est fragile. Deux modes possibles pour l'app : (a) embarquer dist/ et parler à l'API du VPS par HTTPS (permet un écran de connexion hors ligne et l'appairage) ; (b) server.url pointé sur le VPS (mises à jour du frontend instantanées, mais écran blanc hors ligne). Je conseille (a), avec une API versionnée, et l'appairage par QR code qui contient l'URL du VPS et un jeton à usage unique (même modèle qu'OpenClaw et que le QR Wi-Fi actuel). La PWA reste disponible en parallèle pour iOS et pour ceux qui ne veulent pas d'APK.

2) Notifications, une seule voie côté serveur : FastAPI émet du Web Push RFC 8030 chiffré et signé VAPID (par exemple avec pywebpush ; je n'ai pas vérifié l'état de cette bibliothèque). La même implémentation sert :
- la PWA dans le navigateur ;
- l'app Android via UnifiedPush, dont la spec est désormais compatible Web Push ;
- les téléphones avec Google via l'embedded FCM distributor de UnifiedPush, en repli.
Il n'existe pas de plugin Capacitor UnifiedPush (aucun trouvé) : il faut en écrire un petit en Kotlin autour de org.unifiedpush.android:connector et de embedded_fcm_distributor. Proposer ntfy en distributeur, éventuellement auto-hébergé sur le VPS à côté de Caddy. Ajouter un mode « connexion permanente » optionnel, à la manière de Home Assistant Local Push : service au premier plan, WebSocket vers le VPS, notification persistante. C'est utile pour les appels de l'agent sur un téléphone sans Google ni distributeur.

3) iOS : il n'y a aucun chemin sans Apple. Une PWA sur iOS 16.4+ passe de toute façon par l'infrastructure push d'Apple, et une app native passe par APNs (compte développeur à 99 $/an, Mac et Xcode pour compiler). Il faut le dire honnêtement au public. Le contenu reste confidentiel si on n'envoie qu'un réveil (ID de message) et que l'app récupère le message sur le VPS, comme le poll_request de ntfy.

4) Construire l'APK en local : JDK 21 obligatoire (JDK 17 ne suffit pas), Node 22+, SDK Android API 36. Le JDK 21 est confirmé officiellement pour Capacitor 7 ; pour la v8, la doc officielle ne donne pas de numéro et c'est Capgo qui confirme JDK 21.
- Une fois : npm i @capacitor/core @capacitor/cli @capacitor/android && npx cap init "Noah" app.noah.agent --web-dir dist && npx cap add android
- À chaque build : npm run build && npx cap sync android && cd android && ./gradlew assembleDebug (sortie : android/app/build/outputs/apk/debug/app-debug.apk)
- Release signée : npx cap build android --androidreleasetype APK --keystorepath noah.jks --keystorepass … --keystorealias noah --keystorealiaspass …
Pour la CI, utiliser une image avec JDK 21 et le SDK Android, ou GitHub Actions avec actions/setup-java (distribution temurin, java-version 21).

5) Ce qui manque à une PWA face à une app native :
- Android : la PWA a Web Push, mais dans Chrome il passe par FCM, donc Google. C'est ce que je sais, pas confirmé par les sources de cette recherche. Web Share Target existe mais seulement si la PWA est installée. Il n'y a pas de service au premier plan, donc pas de connexion permanente ni d'appel fiable quand l'app est fermée. Pas de UnifiedPush, pas de notifications d'appel plein écran, pas de démarrage au boot, pas de raccourci micro système.
- iOS : push seulement après ajout à l'écran d'accueil, avec une fiabilité irrégulière. Pas de Web Share Target (bug WebKit ouvert depuis 2019), pas de Background Sync, pas d'exécution en arrière-plan, stockage plus limité. Statut UE ambigu.
- Le micro (getUserMedia) marche en PWA au premier plan des deux côtés, mais jamais en arrière-plan.
- Il manque aussi la distribution en magasin (Play, F-Droid) qui rassure le public visé.

Non trouvé ou non vérifié :
- le framework de l'app OpenClaw et de Conduit ;
- le JDK officiel exact pour Capacitor 8 ;
- l'état de la prise en charge de VAPID et du correctif côté ntfy ;
- le statut actuel des PWA iOS dans l'UE.

On garde le frontend React/PWA existant et on ajoute des plugins natifs : push, système de fichiers, partage, micro. La doc est celle de la v8. Elle exige Android Studio 2025.2.1 minimum, le SDK API 24 ou plus, et la dernière version stable est Android 16 (API 36). Elle dit que le JDK n'a pas à être installé séparément, puisqu'Android Studio fournit le sien. Elle ne donne aucun numéro de JDK.

AGP 8.13.0, wrapper Gradle 8.14.3, minSdk 24, compileSdk et targetSdk 36, Kotlin 2.2.20, Node.js 22 ou plus. Cette page ne cite pas non plus de version de JDK.

Options utiles : --signing-type apksigner et --flavor.

C'est donc une migration, pas un simple emballage.

Expo « gère la complexité » de FCM et d'APNs, et l'envoi documenté passe par l'API Expo Push Service, donc par un tiers. Cette page ne dit pas si on peut envoyer directement vers FCM ou APNs. Ça va contre l'objectif « sans tiers ».

Le push n'existe que par des plugins communautaires (FCM ou APNs). Aucun plugin de push officiel n'a été trouvé. Le README de https://github.com/yanqianglu/tauri-plugin-mobile-push prévient que les méthodes basées sur le swizzling peuvent échouer sans erreur sur iOS 26 et plus. Il faut un service non exporté qui étend PushService (action org.unifiedpush.android.connector.PUSH_EVENT), puis UnifiedPush.tryUseCurrentOrDefaultDistributor() et UnifiedPush.register(). La doc conseille de se réenregistrer de temps en temps. Attention au conflit de dépendance Tink : il faut épingler sa version.

Les messages passent par FCM. VAPID est facultatif chez la plupart des distributeurs mais obligatoire avec FCM. Spec Android : https://unifiedpush.org/developers/spec/android/ (sans clé VAPID valide, l'enregistrement échoue avec REGISTRATION_FAILED).
- **KDE KUnifiedPush : point d'étape sur Web Push (avril 2025)** (https://planet.kde.org/volker-krause-2025-04-18-kunifiedpush-web-push-update) : Confirme que la spec UnifiedPush est désormais compatible Web Push (RFC 8030), avec VAPID (RFC 8292) et chiffrement des messages. Conséquence pratique : le serveur FastAPI peut garder un seul émetteur Web Push (VAPID) qui sert à la fois la PWA (navigateur), UnifiedPush et FCM par le distributeur embarqué. L'article signale aussi un petit problème de compatibilité avec ntfy dans certaines configurations ; je n'ai pas trouvé si le correctif a été fusionné.

Clés : web-push-public-key, web-push-private-key, web-push-file et web-push-email-address (paire générée par 'ntfy webpush keys'). Il faut du HTTPS avec un certificat valide. **Pièges.**
- Le JDK : Capacitor 7 et 8 demandent JDK 21. Avec JDK 17, l'erreur est 'invalid source release: 21'. Il faut faire pointer JAVA_HOME vers JDK 21, ou utiliser le JBR fourni par Android Studio.
- La doc officielle de Capacitor 8 ne donne pas de numéro de JDK : JDK 21 n'est confirmé que par un blog tiers (Capgo). À vérifier dans android/variables.gradle et build.gradle générés.
- Capacitor 8 exige Node 22+ et Android Studio 2025.2.1+. Un vieux wrapper Gradle avec JDK 21 casse le build : utiliser Gradle 8.14.3 et AGP 8.13.0.
- Le plugin officiel @capacitor/push-notifications repose sur Firebase/FCM côté Android. L'utiliser contredit la promesse « sans tiers » : il faut un plugin UnifiedPush maison.
- UnifiedPush embarque Tink, et un conflit de classes dupliquées est fréquent : il faut épingler la version de Tink dans Gradle.
- FCM (y compris l'embedded distributor) exige VAPID : sans clé valide, l'enregistrement échoue avec REGISTRATION_FAILED. Générer une paire VAPID par instance et ne jamais la changer, sinon tous les abonnements sont perdus.
- iOS : aucun push sans Apple. ntfy auto-hébergé sans upstream-base-url ntfy.sh peut avoir plusieurs heures de retard. Avec ce réglage, un ID et un hash passent par ntfy.sh. La régression 2.10.0 ('New message' au lieu du contenu) est à vérifier.
- PWA iOS : seul Safari installe ; push seulement après ajout à l'écran d'accueil et après un geste de l'utilisateur. Statut UE flou depuis l'épisode iOS 17.4.
- Web Push sur Chrome Android passe par les serveurs de Google : une PWA seule n'est pas « sans tiers » sur Android.
- server.url pointé sur le VPS : écran blanc hors ligne, et rejet probable sur l'App Store (app trop proche d'un site web). Embarquer dist/ est plus sûr.
- Un service au premier plan avec WebSocket permanent doit déclarer son type (foregroundServiceType) sur les Android récents et rester visible. Mal fait, Android le tue, ou Google Play le refuse.
- OpenClaw montre le risque de l'appairage : note Play Store de 2,2/5 pour pannes d'appairage et instabilité. Tester l'appairage QR sur de vrais réseaux (4G, NAT, certificat Caddy).
- Expo DOM components ne convient pas à une SPA Vite entière : migration de la navigation, et push via Expo Push Service (tiers).
- Tauri mobile : push seulement par des plugins communautaires ; le swizzling iOS risque de ne plus marcher sur iOS 26+ ; il faut une chaîne Rust en plus.

## mises-a-jour

**Recommandation.** Ne pas utiliser Watchtower. L'original est archivé depuis le 17/12/2025, et le README du fork nickfedor le déconseille en production. Ne pas brancher non plus un outil tiers qui recréerait les conteneurs dans le dos du lanceur. Le lanceur de Noah parle déjà à Docker et crée un conteneur Hermes et un Camoufox par agent : c'est lui qui doit porter un « updater » maison, sur la mécanique de WUD (préchargement, hook pre bloquant, rollback piloté par la santé) et l'ergonomie de Home Assistant et d'Umbrel.

1) Un manifeste de release signé, publié par Noah. Comme Coolify avec son fichier de versions sur CDN, Noah publie un manifeste signé (minisign ou cosign, par exemple) qui fige un ensemble testé ensemble : version de l'app (serveur et front), digest de nousresearch/hermes-agent pris uniquement sur le tag stable, couple paquet camoufox et binaire navigateur intégré à l'image au build, digest de caddy:2.11.x, version minimale des apps bureau et mobile, type de changement (patch, mineure, majeure), notes, migrations. On ne suit jamais de tag flottant côté VPS : Caddy reconstruit 2.11.7 sous le même nom (30/10/2026) et Hermes déplace stable par promotion. Le VPS tire des digests.

2) Un temps de rodage avant de promouvoir. Hermes a publié v0.22.1 par erreur et l'a remplacée par v0.22.2 le lendemain. Camoufox ne sort que des -beta. Noah attend donc N jours (3 à 7, par exemple) et sa propre CI (démarrage, /health, scénario agent et navigateur) avant de mettre un digest amont dans son manifeste. Il prévoit deux canaux : « stable » et « en avance » pour les volontaires.

3) Vérifier souvent, installer rarement. Vérification chaque heure (le défaut de Coolify). Préchargement des images en arrière-plan (le PRELOAD de WUD) pour que la coupure ne dure que le temps de la recréation.

4) Choisir le moment. Fuseau de l'utilisateur, demandé à l'installation, pas celui du VPS. On tient un histogramme par heure de la semaine : messages envoyés, sessions PWA, bureau et mobile ouvertes, tâches et crons Hermes, sessions Camoufox actives. On prend le créneau le plus creux sur les 2 à 4 dernières semaines, comme les heures d'activité automatiques de Windows. Tant qu'il n'y a pas assez de données, on prend 03:00 à 05:00 heure locale, comme Automatic-Reboot-Time 03:00 ou le minuit de Coolify. On ajoute un délai aléatoire pour étaler la charge sur le registre (RandomizedDelaySec, comme le conseille Debian). Juste avant d'agir, un contrôle bloquant : aucune tâche agent en cours, aucun cron Hermes dans les X minutes, aucune session navigateur ouverte. Sinon on repousse de 30 minutes, jusqu'à une limite. Exception : un correctif de sécurité marqué urgent dans le manifeste passe dans les 24 h, avec notification préalable. On aligne aussi le redémarrage d'unattended-upgrades (sécurité seulement) sur ce même créneau.

5) Sauvegarder d'abord, et bloquer si ça échoue. Comme Coolify et le hook pre de WUD : on fait un instantané de chaque volume /opt/data (state.db, en arrêtant l'agent ou via l'API de sauvegarde SQLite, plus config.yaml, .env, memories/, skills/, cron/), de la base de l'app, du profil Camoufox et de la config Caddy, avec une rétention de N copies. La migration automatique de Hermes ne sauvegarde que config.yaml et .env, pas state.db.

6) Appliquer par étapes, avec contrôle de santé. Ordre : un agent canari, puis les autres agents, puis Caddy, puis l'app. On garde l'ancien conteneur sous un nom temporaire (le ROLLBACK de WUD). Santé : GET /health de Hermes sur 8642 (il faut API_SERVER_ENABLED=true, exposé seulement sur le réseau Docker interne), puis /health/detailed en lisant le champ status, car il renvoie 200 même dégradé. Puis la santé de l'app et un vrai test bout en bout (une requête agent, une page ouverte dans Camoufox). Fenêtre de 5 minutes (le défaut de WUD). Pour le serveur FastAPI derrière Caddy, docker-rollout permet une bascule sans coupure.

7) Revenir en arrière automatiquement, avec les données. Si la santé échoue, on remet l'ancien conteneur et on restaure l'instantané, car Hermes migre la config vers l'avant et Immich ne prend pas en charge le retour arrière. On bloque ce digest sur cette instance et on remonte un rapport anonymisé, si l'utilisateur l'accepte.

8) Les majeures ne sont jamais automatiques. Elles se reconnaissent au semver du manifeste (pour Hermes en 0.x, un saut de 0.Y compte comme une majeure, vu que v0.22.0 a déplacé des composants en plugins) ou à un drapeau migration_required. On notifie, avec un résumé en langage clair, le lien vers le changelog et une estimation de la coupure. L'utilisateur choisit « installer cette nuit », « maintenant » ou « ignorer cette version ». C'est l'approche d'Immich (majeure verrouillée par IMMICH_VERSION) et d'Umbrel (rien ne s'installe sans l'accord de l'utilisateur).

9) Notifier comme Home Assistant. On expose dans l'API un objet par composant : installed_version, latest_version, release_summary, release_url, skipped_version, état, prochain créneau prévu, avec les actions install(version, backup=true), skip et clear_skipped. On pousse par Web Push vers la PWA, FCM ou ntfy vers Android, et l'app de bureau. Message avant (« mise à jour prévue cette nuit à 3 h 40 ») et après (succès ou retour arrière).

10) L'app elle-même. Le lanceur ne peut pas se remplacer pendant qu'il tourne : il démarre un conteneur helper éphémère, comme l'étape « Helper » de Coolify. Ce helper recrée le lanceur, vérifie sa santé et revient en arrière si besoin. Côté clients : electron-updater avec stagingPercentage pour le bureau. Sur Android, Play In-App Updates si l'app passe par le Play Store, sinon un contrôle maison contre le manifeste. Le serveur garde une compatibilité d'API N-1 et annonce la version minimale de client, pour qu'un téléphone pas encore mis à jour ne casse pas.

- **Watchtower (containrrr, original)** (https://github.com/containrrr/watchtower) : Il a popularisé le principe : tirer la nouvelle image, arrêter le conteneur proprement, le recréer avec les mêmes options. Les installations existantes continuent de tourner. Le dépôt est archivé depuis le 17 décembre 2025 (lecture seule, « This project is no longer maintained »). Plus aucune version ni correctif de sécurité. Selon Linuxiac (https://linuxiac.com/docker-update-tool-watchtower-reaches-end-of-maintenance/), les mainteneurs principaux sont partis. À ne pas utiliser pour Noah.
- **Watchtower, fork nicholas-fedor** (https://github.com/nicholas-fedor/watchtower) : Fork actif (image nickfedor/watchtower, doc https://watchtower.nickfedor.com/, la doc « latest » renvoie vers v1.23.2). Il propose une planification cron avec fuseau horaire, des lifecycle hooks, une API HTTP (endpoints check, update, history, health) et des notifications Shoutrrr. --schedule / WATCHTOWER_SCHEDULE prend un cron à 6 champs et exige TZ ou /etc/localtime monté (page configuration/scheduling). --interval vaut 86400 s par défaut. Le README dit en propres termes : « We do not recommend using Watchtower in a commercial or production environment ». Je n'ai trouvé dans la doc aucun retour arrière automatique après un contrôle de santé raté.
- **What's Up Docker (WUD)** (https://getwud.app/docs/configuration/triggers/docker/) : C'est le modèle le plus proche de ce qu'il faut à Noah. Le trigger Docker recrée le conteneur, accepte des hooks pre capables d'annuler la mise à jour, et revient en arrière automatiquement selon le HEALTHCHECK. La doc affiche la version 9.x. AUTO=false avec PRELOAD=true télécharge l'image en avance sans toucher au conteneur. PRUNE nettoie les vieilles images. Un hook pre qui échoue (exemple de la doc : mysqldump) annule tout et laisse l'ancien conteneur en place. ROLLBACK garde l'ancien conteneur sous un nom temporaire. Avec HEALTHCHECK, WUD attend jusqu'à ROLLBACKWINDOW (300 000 ms par défaut) en sondant toutes les ROLLBACKINTERVAL (10 000 ms). Sans HEALTHCHECK, le nouveau conteneur doit tenir ROLLBACKGRACE (10 000 ms). Labels possibles : wud.rollback.enable, wud.rollback.window. Le rollback est ignoré si le conteneur a AutoRemove.
- **Diun** (https://crazymax.dev/diun/) : Il ne fait que détecter et notifier, sans jamais toucher aux conteneurs. Il repère un nouveau tag ou un nouveau digest selon un planning intégré. Sources surveillées : Docker, Containerd, Kubernetes, Swarm, Nomad, Dockerfile, File. Canaux : ntfy, Gotify, Matrix, Signal, Webhook, Script, Apprise, Telegram, etc. Le guide de migration le plus récent visible va de v4.1 à v4.29. Bon modèle pour une détection seule, à combiner avec un applicateur.
- **Coolify (mise à jour de l'instance)** (https://coolify.io/docs/core/instance-management/update) : Deux réglages séparés, la vérification et l'installation. La sauvegarde de la base sert de garde-fou : si elle échoue, la mise à jour ne démarre pas. Update Check Frequency vaut 0 * * * * (chaque heure) par défaut. Elle lit un fichier de versions sur un CDN. Auto Update Frequency vaut 0 0 * * * (minuit, fuseau de l'instance) par défaut et accepte cron ou préréglages. La variable AUTOUPDATE dans /data/coolify/source/.env court-circuite le tableau de bord. Étapes affichées : Preparing, Helper, Image, Restart (un conteneur helper fait la mise à jour). Indisponibilité : moins d'une minute. Le script upgrade.sh exige un numéro de version explicite, sinon COOLIFY_VERSION=latest casse les vérifications. Journaux : /data/coolify/source/upgrade-*. La doc conseille de vérifier qu'aucun déploiement n'est en cours.
- **Umbrel (umbrelOS et apps)** (https://umbrel.com/support/basics/updating-umbrelos) : Les mises à jour arrivent par OTA mais ne s'installent jamais seules. Une notification apparaît sur l'écran d'accueil. Si la mise à jour échoue, le système revient seul à la version précédente sans perte de données. Citation : « are never installed automatically ». Le système revient automatiquement à la version précédente en cas d'échec. Le mécanisme n'est pas documenté (rien sur des partitions A/B). Les apps ne se mettent pas à jour seules non plus : un badge s'affiche sur l'App Store (https://umbrel.com/support/apps/how-to-update-an-app). Une vieille doc dev (git.lu.ke/lukechilds/umbrel, scripts/update/README.md) décrit sauvegarde avant, installation, contrôle après et sommes de contrôle signées, mais elle date peut-être.
- **Home Assistant (entité update)** (https://www.home-assistant.io/integrations/update) : Un modèle de données propre pour présenter une mise à jour à l'utilisateur : version installée, dernière version, résumé, lien, version ignorée, et une action d'installation avec sauvegarde. Attributs : installed_version, latest_version, release_summary, release_url, title, skipped_version. Actions : update.install, update.skip, update.clear_skipped. Déclencheur : update.became_available. Selon https://www.home-assistant.io/actions/update.install/, update.install prend version (optionnel) et backup (booléen, false par défaut, « Create a backup before installing the update »), si l'intégration le permet. La majeure est verrouillée par une variable explicite (IMMICH_VERSION), donc un simple pull ne fait jamais sauter de majeure. Réponse acceptée : « Immich follows proper semantic versioning starting at v2 » (auteur goalie2002, son statut de mainteneur n'est pas indiqué). D'après le résumé de recherche, les notes de la v3.0.0 listent des cassures, surtout d'API, avec un guide de migration, et la mise à jour consiste à passer IMMICH_VERSION de v2 à v3 puis pull et up. Doc d'upgrade (prévisualisation, https://docs.pr-30460.preview.immich.app/install/upgrading) : lire les notes de version, puis docker compose pull && docker compose up -d. Un blog (https://mustafa.net/2026/10/10/immich-v2-to-v3-upgrade/) rappelle que le tag v2 bouge à l'intérieur de la 2.x et conseille un dump de la base avant le saut de majeure. Le retour à une version antérieure n'est pas pris en charge selon un guide tiers (lumadock.com) : revenir en arrière veut dire restaurer une sauvegarde. Je n'ai pas trouvé de page officielle unique décrivant la politique.
- **unattended-upgrades (Debian/Ubuntu, OS du VPS)** (https://wiki.debian.org/UnattendedUpgrades) : Correctifs de sécurité de l'hôte posés automatiquement, avec un redémarrage programmé à une heure locale choisie. Par défaut, seule la sécurité passe (Origins-Pattern). Unattended-Upgrade::Mail sert à notifier. apt-daily.timer télécharge, apt-daily-upgrade.timer installe. Je les ai trouvés dans des guides tiers (https://linuxcapable.com/how-to-configure-unattended-upgrades-on-ubuntu-linux, https://oneuptime.com/blog/post/2026-03-02-configure-unattended-upgrades-security-patches-ubuntu/view), qui donnent aussi les horaires par défaut des timers : 6 h et 18 h pour apt-daily, 6 h pour apt-daily-upgrade, avec délai aléatoire. À vérifier dans le guide serveur Ubuntu officiel.

Réglage : Settings > Windows Update > Advanced options > Active hours > Automatically, ou heures manuelles. Disponible depuis Windows 10 1903. Microsoft ne publie pas l'algorithme d'apprentissage.

Tags : stable = latest (déplacés seulement par une promotion de release complète), main (dev), X.Y.Z figé, digest pour la reproductibilité. Sur Docker Hub (API v2 tags), stable et v0.22.5 datent du 23/10/2026, après rc.1 à rc.3 le 22-23/10. Il existe aussi des variantes -desktop et des tags par architecture. /opt/data contient .env, config.yaml, SOUL.md, sessions/, memories/, skills/, cron/, logs/ et state.db (WAL, risque de corruption sur virtiofs/9p). HERMES_SKIP_CONFIG_MIGRATION=1 coupe la migration automatique. Pas de HEALTHCHECK Docker documenté. Sonde : GET /health sur le port 8642, qui renvoie {"status":"ok"} et demande API_SERVER_ENABLED=true, avec écoute sur 127.0.0.1 par défaut (https://hermes-agent.nousresearch.com/docs/user-guide/features/api-server). GET /health/detailed demande un bearer et renvoie HTTP 200 même dégradé : il faut lire le champ status. Releases (https://github.com/NousResearch/hermes-agent/releases) : semver 0.x, v0.22.0 le 13/10/2026 (composants déplacés en plugins avec migration automatique), v0.22.1 publiée par erreur puis remplacée par v0.22.2. Le « pipeline stable » existe depuis v0.21.6. Les anciens tags suivaient le calendrier (v2026.9.24).
- **Camoufox** (https://github.com/daijro/camoufox/releases) : Projet très actif, avec un train de releases deux fois par mois (PR #864). Le paquet Python et le binaire du navigateur sont versionnés séparément. Dernière release : v158.0.1-beta.41 (Firefox 158.0.1, uBlock Origin 1.75.0), le 29 octobre, marquée Latest. Les précédentes sont des pre-releases (beta.37 à beta.40). Toutes portent le suffixe -beta. Paquet PyPI camoufox 0.5.9 (https://pypi.org/project/camoufox/0.5.9/), la 0.5.7 date du 4/10/2026. Le navigateur appairé s'installe au premier lancement : sans précaution, un conteneur peut télécharger un binaire au démarrage. Il faut l'intégrer dans l'image au build et figer le couple paquet + navigateur.
- **Caddy (image officielle)** (https://hub.docker.com/_/caddy) : Les tags flottants 2 / 2.11 / 2.11.7 sont reconstruits régulièrement (correctifs de l'image de base), ce qui apporte les correctifs de sécurité sans changer de version. D'après l'API Docker Hub (https://hub.docker.com/v2/repositories/library/caddy/tags), latest, 2, 2.11 et 2.11.7 ont été reconstruits le 30/10/2026. Un même tag change donc de digest. Il faut suivre le digest et non le tag, sinon on rate les reconstructions ou on les applique sans contrôle.
- **docker-rollout** (https://github.com/Wowu/docker-rollout) : Plugin Docker CLI pour Compose, sans coupure : il double le service, attend le healthcheck, puis retire l'ancien conteneur. docker rollout <service> remplace docker compose up -d <service>. Sans healthcheck, il attend --wait (10 s par défaut). --wait-after-healthy est disponible. Il faut un proxy (Traefik, nginx-proxy, Caddy), ni container_name ni ports publiés. Utile pour le serveur FastAPI derrière Caddy, pas pour un agent avec état comme Hermes.

Exige Android 5.0+ et Google Play à l'exécution. Ne marche donc pas pour un APK installé hors Play ou distribué via F-Droid : il faut alors un contrôle de version maison auprès du serveur. **Pièges.**
- Watchtower original : archivé depuis le 17/12/2025, sans correctifs de sécurité alors qu'il a accès au socket Docker. Le fork nickfedor déconseille lui-même la production, et je n'ai trouvé chez lui aucun retour arrière après un contrôle de santé raté.
- Suivre des tags au lieu des digests : caddy:2.11.7 est reconstruit sous le même nom, et hermes-agent:stable/latest bougent à chaque promotion. Sans digest, impossible de savoir ce qui tourne ni de revenir à l'état exact.
- Prendre le tag latest de Hermes pour un tag de dev : chez Hermes, latest = stable, et main est le canal de dev. Il ne faut jamais suivre main ni les tags rc.*. Il faut aussi choisir la bonne variante (-desktop ou non) et la bonne architecture (amd64 ou arm64).
- Hermes 0.x : le semver de la série 0 n'assure pas la compatibilité entre mineures. v0.22.0 a déplacé des composants en plugins, et v0.22.1 a été publiée depuis le mauvais commit. Un temps de rodage s'impose avant promotion.
- La migration de config de Hermes ne sauvegarde que config.yaml et .env, pas state.db. Revenir à l'ancienne image sans restaurer les données peut échouer sur une config déjà migrée.
- state.db en mode WAL se corrompt sur les montages virtiofs/9p (Docker Desktop sur macOS ou Windows) : c'est un risque pour le mode local Electron. Il faut des volumes nommés, et pour la sauvegarde l'API backup de SQLite ou l'arrêt du conteneur plutôt qu'une simple copie de fichiers.
- /health de Hermes n'est qu'une sonde de vivacité qui demande API_SERVER_ENABLED=true. /health/detailed renvoie 200 même dégradé : il faut lire status. Il n'y a pas de HEALTHCHECK Docker natif documenté, donc sans test maison WUD ou docker-rollout ne vérifient que « le conteneur tourne ».
- Camoufox installe son navigateur au premier lancement et ne sort que des -beta, deux fois par mois. Sans binaire intégré et figé dans l'image, chaque recréation peut tirer une version différente, voire échouer hors ligne.
- Le paquet Python camoufox et le binaire du navigateur évoluent séparément (0.5.9 contre v158.0.1-beta.41) : il faut figer le couple, sinon on risque une incompatibilité.
- Le fuseau du VPS est souvent UTC : un créneau « 3 h » sans le fuseau de l'utilisateur tombe en pleine journée pour lui. Le cron de Watchtower demande lui aussi TZ explicitement.
- Un agent qui tourne 24 h/24 n'a pas d'heure creuse sûre : il faut aussi tenir compte des crons Hermes (cron/) et des tâches longues, pas seulement de l'activité humaine.
- Le lanceur qui se met à jour lui-même : s'il se tue avant d'avoir recréé le nouveau conteneur, l'instance est morte. Il faut un helper éphémère séparé, comme Coolify.
- Coolify : appeler upgrade.sh sans version écrit COOLIFY_VERSION=latest et casse les vérifications suivantes. C'est le même piège pour install.sh de Noah s'il sert aussi à la mise à jour, et Coolify interdit justement install.sh pour mettre à jour.
- Home Assistant a retiré la case « sauvegarde avant mise à jour » du panneau en 2025.1.1 : si la sauvegarde reste une option facultative de l'interface, elle sera oubliée. Chez Noah, elle doit être imposée par le pipeline.
- Android : Play In-App Updates ne marche que via Google Play. Un APK installé hors Play ou distribué via F-Droid demande un mécanisme maison, et le public visé (vie privée) évite souvent Play.
- Mise à jour du serveur sans compatibilité d'API N-1 : les téléphones et bureaux pas encore à jour cassent. Il faut publier la version minimale de client dans le manifeste.
- Les mises à jour automatiques de l'OS (unattended-upgrades) peuvent redémarrer le VPS ou relancer dockerd hors créneau : il faut aligner Automatic-Reboot-Time et vérifier que les conteneurs ont une politique restart.
- Informations non trouvées ou non confirmées : la doc nickfedor sur monitor-only, rolling-restart et label-enable n'a pas été lue ; l'algorithme des heures d'activité de Windows n'est pas public ; le mécanisme de retour arrière d'umbrelOS n'est pas documenté ; les options Automatic-Reboot-* viennent de guides tiers ; je n'ai pas trouvé de page officielle unique sur la politique de versions d'Immich.

## concurrents

**Recommandation.** Noah doit reprendre ce qui marche chez OpenClaw et Hermes, en enlevant ce qui inquiète un public soucieux de sa vie privée.

3) Relier le bureau et le téléphone. Un QR ou code de setup à usage unique et à courte durée de vie, émis par le VPS sur une URL wss:// publique en TLS (pas seulement sur le Wi-Fi), puis une approbation explicite de l'appareil côté serveur. Garder ce que les utilisateurs aiment : messages en file d'attente hors ligne, cartes natives pour approuver une action ou répondre à l'agent. Corriger ce qui bloque : messages d'erreur clairs (QR expiré, version incompatible, appareil en attente), et un client mobile qui tolère des versions décalées. Android d'abord : une app légère (PWA empaquetée en TWA, ou Capacitor) avec UnifiedPush/ntfy auto-hébergé pour les notifications, au lieu d'un relais tiers comme celui d'OpenClaw pour iOS.

4) Des mises à jour qui ne dérangent pas. Une fenêtre de maintenance apprise sur l'inactivité de l'utilisateur, et jamais pendant une tâche en cours. Snapshot des volumes et de la config avant chaque mise à jour, contrôle de santé après le redémarrage de tous les services (agent, gateway, dashboard, navigateur, WebSocket derrière Caddy), puis retour arrière automatique en cas d'échec. Les issues Hermes #58578 et #56775, et le refus de rollback d'OpenClaw après migration, montrent exactement ce qu'il faut éviter.

5) Des coûts sous contrôle. Plafond de dépense par jour et par agent, compteur de tokens visible, contexte compact, pas de boucles de veille qui appellent un gros modèle.

6) Des skills de confiance. Pas de place de marché ouverte. Des skills signés ou vérifiés et sans prérequis à installer à la main, pour éviter l'équivalent de ClawHavoc.

7) Vie privée vérifiable. Aucune télémétrie, chaque flux sortant listé, et le choix du fournisseur de modèle (local, OpenRouter, etc.) affiché dans l'interface. Le navigateur Camoufox par agent est un atout face à ChatGPT agent, qui conserve historique et captures : il faut l'expliquer, avec une prise en main du navigateur façon takeover et aucune capture pendant que l'utilisateur tape un mot de passe.

**Pièges.**
- Le token d'administration dans des variables d'environnement visibles depuis le panneau de l'hébergeur, comme le gateway token du template Hostinger d'OpenClaw. Quiconque accède au panneau prend le contrôle de l'agent.
- Un bind sur toutes les interfaces sans authentification. C'est la cause des dizaines de milliers d'instances OpenClaw exposées.
- Un appairage limité au Wi-Fi local ou au ws:// en clair. Les apps OpenClaw refusent le ws:// vers un hôte public : il faut wss:// avec un vrai certificat, ou Tailscale Serve.
- Des notifications iOS qui dépendent d'un relais hébergé par l'éditeur (le relais APNs d'OpenClaw détient les tokens). C'est contraire à la promesse d'auto-hébergement, et il faut le dire honnêtement si iOS arrive un jour.
- Une mise à jour qui ne relance qu'une partie des processus, ou qui casse le WebSocket derrière le proxy (issues Hermes #58578 et #56775), ou des migrations de base irréversibles qui bloquent tout retour arrière (OpenClaw `state-migrated-no-rollback`).
- Un contexte trop gros réinjecté à chaque message, des boucles de veille sur un modèle cher, des crédits brûlés par des tâches qui échouent (OpenClaw, Manus). Sans compteur ni plafond, l'utilisateur perd confiance.
- Une place de marché de skills ouverte et non vérifiée (ClawHavoc : 341 skills malveillants sur 2 857 audités, voleur AMOS installé via de faux prérequis).
- Compiler les images Docker sur un petit VPS : lent, sujet aux pannes, et pas reproductible. Mieux vaut des images signées et préconstruites.
- Des sources souvent secondaires ou commerciales. Les synthèses Reddit (Kilo, BetterClaw), les résumés IA de vidéos (pulse.bot, lilys.ai) et les chiffres d'instances exposées sont à recouper. Le statut actuel de ChatGPT agent (remplacé par « ChatGPT Work » ?) n'a pas pu être vérifié : page en 403. Aucune issue GitHub OpenClaw précise sur l'appairage n'a été retrouvée, et aucune app mobile officielle d'Hermes n'existe à ma connaissance.
- Un fournisseur de modèle américain mis par défaut (OpenAI, ou un routeur IA de l'hébergeur comme Hostinger AI Router). Le public visé veut justement éviter de confier ses données à OpenAI ou xAI, il faut donc afficher le choix et le laisser à l'utilisateur.
